# Лабораторная работа: диагност сетевого подключения

# Вариант 5

## Общая идея

Разработать консольное приложение для диагностики проблем с сетевым подключением.

Программа должна последовательно проверить:

* наличие сетевого интерфейса и его конфигурацию;
* доступность локального шлюза;
* доступность узла в интернете по IP-адресу;
* работу DNS;
* доступность заданных веб-ресурсов;
* маршрут до выбранного узла;
* задержку и потери пакетов.

Приложение должно запускать системные сетевые утилиты, получать их вывод, извлекать из него результаты и формировать понятное заключение.

Основной сценарий использования возникает, когда пользователь сталкивается с медленной работой сети, отсутствием интернета или недоступностью отдельного сайта. Сформированный отчёт можно использовать самостоятельно либо передать системному администратору или провайдеру.

Программа не должна изменять сетевые настройки компьютера.

# 1. Работа с приложением

Приложение должно управляться через текстовые команды или меню.

Пользователь должен иметь возможность:

** запустить полную диагностику;
** выполнить отдельную проверку;
** выбрать диагностический профиль;
** указать дополнительный узел для проверки;
** посмотреть результаты текущей диагностики;
** посмотреть сохранённые результаты предыдущих запусков;
** сравнить два результата;
** сформировать текстовый отчёт;
** перезагрузить конфигурацию;
** завершить работу.

Пример командного интерфейса:

```text
> profiles
> diagnose home
> ping gateway
> dns example.com
> http https://example.com
> trace example.com
> results
> history
> compare 12 15
> report
> reload
> exit
```

Разрешается реализовать нумерованное меню.

Типичный сценарий полной диагностики:

1. Пользователь выбирает профиль.
2. Программа проверяет наличие необходимых системных утилит.
3. Собирает сведения о сетевом интерфейсе и шлюзе.
4. Проверяет доступность шлюза.
5. Проверяет доступность внешнего IP-адреса.
6. Проверяет разрешение доменных имён.
7. Проверяет доступность веб-ресурсов.
8. При необходимости выполняет трассировку.
9. Анализирует собранные результаты.
10. Показывает предполагаемый источник проблемы.
11. Сохраняет результат и формирует отчёт.

# 2. Используемые системные утилиты

Студент должен выбрать одну поддерживаемую операционную систему:

* Windows;
* Linux;
* macOS.

Поддержка сразу нескольких операционных систем не является обязательной.

Приложение должно запускать внешние процессы, получать код их завершения, стандартный вывод и стандартный поток ошибок.

## Windows

Для реализации под Windows необходимо использовать:

* `ipconfig` — получение сведений о сетевых интерфейсах, IP-адресах и шлюзах;
* `ping` — проверка доступности и сбор статистики задержек и потерь;
* `nslookup` — проверка разрешения доменных имён;
* `tracert` — определение маршрута до удалённого узла;
* `curl` — проверка HTTP- и HTTPS-ресурсов.

Примеры вызовов:

```text
ipconfig /all
ping -n 10 -w 2000 192.168.1.1
nslookup example.com
tracert -d example.com
curl --head --location --max-time 10 https://example.com
```

`ping` в Windows выводит время прохождения пакетов и итоговую статистику, `tracert` строит маршрут до узла, `nslookup` выполняет DNS-запросы, а `ipconfig` показывает текущую конфигурацию TCP/IP.

## Linux

Для реализации под Linux необходимо использовать:

* `ip address` — получение сведений о сетевых интерфейсах и адресах;
* `ip route` — получение маршрута по умолчанию и адреса шлюза;
* `ping` — проверка доступности и сбор статистики;
* `nslookup` или `dig` — проверка DNS;
* `traceroute` — определение маршрута;
* `curl` — проверка HTTP- и HTTPS-ресурсов.

Примеры вызовов:

```text
ip address
ip route
ping -c 10 192.168.1.1
nslookup example.com
traceroute -n example.com
curl --head --location --max-time 10 https://example.com
```

Утилиты `nslookup` и `traceroute` могут поставляться отдельными пакетами. Если выбранная утилита отсутствует, приложение должно сообщить её имя и отказаться только от соответствующей проверки, а не завершать всю диагностику. Команды семейства `ip` позволяют получить сведения об интерфейсах и таблице маршрутизации.

## macOS

Для реализации под macOS необходимо использовать:

* `ifconfig` — получение сведений о сетевых интерфейсах;
* `route -n get default` — получение маршрута по умолчанию и шлюза;
* `ping` — проверка доступности и сбор статистики;
* `nslookup` или `dig` — проверка DNS;
* `traceroute` — определение маршрута;
* `curl` — проверка HTTP- и HTTPS-ресурсов.

Примеры вызовов:

```text
ifconfig
route -n get default
ping -c 10 192.168.1.1
nslookup example.com
traceroute -n example.com
curl --head --location --max-time 10 https://example.com
```

## Проверка зависимостей

Перед началом диагностики программа должна проверить наличие всех необходимых утилит.

Пример:

```text
Проверка системных утилит:

[+] ping
[+] nslookup
[+] curl
[-] traceroute
[+] ip

Проверка маршрута будет недоступна:
утилита traceroute не найдена.
```

Приложение не должно подменять отсутствующую утилиту самостоятельно реализованным аналогом.

# 3. Диагностические профили и конфигурация

Настройки приложения должны храниться в отдельном конфигурационном файле.

Конфигурация должна содержать один или несколько диагностических профилей. Профиль описывает сеть и набор проверок, подходящих для конкретного места или ситуации.

Например:

* домашняя сеть;
* университетская сеть;
* рабочая сеть;
* мобильная точка доступа;
* проверка отдельного сервиса.

Пример конфигурации:

```json
{
  "logFile": "network-diagnostic.log",
  "historyFile": "diagnostic-history.json",
  "reportDirectory": "reports",
  "defaultProfile": "home",

  "profiles": {
    "home": {
      "description": "Домашнее подключение",
      "gateway": "auto",
      "externalIpTargets": [
        "1.1.1.1",
        "8.8.8.8"
      ],
      "dnsNames": [
        "example.com",
        "wikipedia.org"
      ],
      "httpTargets": [
        "https://example.com"
      ],
      "traceTarget": "example.com",
      "pingCount": 10,
      "timeoutMilliseconds": 2000,
      "maximumRouteHops": 20,
      "thresholds": {
        "warningLatencyMilliseconds": 100,
        "criticalLatencyMilliseconds": 300,
        "warningPacketLossPercent": 5,
        "criticalPacketLossPercent": 20,
        "warningHttpTimeMilliseconds": 2000
      }
    }
  }
}
```

В профиле должны задаваться как минимум:

* название и описание;
* адрес локального шлюза либо значение `auto`;
* один или несколько внешних IP-адресов;
* доменные имена для проверки DNS;
* HTTP- или HTTPS-ресурсы;
* узел для трассировки;
* количество отправляемых пакетов;
* время ожидания;
* максимальное количество переходов при трассировке;
* пороги задержки и потерь пакетов.

При значении `gateway: "auto"` приложение должно попытаться определить шлюз с помощью выбранной системной утилиты.

Пользователь должен иметь возможность создать новый профиль через меню приложения. Созданный профиль сохраняется в конфигурационном файле.

# 4. Сбор и представление результатов

Для каждой выполненной проверки программа должна сохранить:

* время начала и завершения;
* запущенную утилиту;
* цель проверки;
* код завершения процесса;
* разобранный результат;
* предупреждения;
* признак полноты результата.

Полный текст вывода утилиты может сохраняться в диагностическом отчёте, но основное представление должно содержать обработанную информацию.

## Проверка доступности

По результатам `ping` необходимо определить:

* количество отправленных пакетов;
* количество полученных ответов;
* процент потерянных пакетов;
* минимальную задержку;
* максимальную задержку;
* среднюю задержку;
* наличие резких скачков задержки.

Пример:

```text
Проверка внешнего узла: 1.1.1.1

Отправлено пакетов: 10
Получено ответов: 9
Потеряно: 10 %

Минимальная задержка: 21 мс
Средняя задержка: 46 мс
Максимальная задержка: 184 мс

Состояние: нестабильное соединение
Причина: обнаружены потери пакетов и скачки задержки.
```

Результат должен сравниваться с порогами выбранного профиля.

Отсутствие ответа на `ping` не должно автоматически означать, что узел не работает: некоторые узлы могут не отвечать на ICMP-запросы. Такой результат необходимо учитывать вместе с DNS- и HTTP-проверками.

## Проверка DNS

Программа должна выполнить запрос для каждого настроенного доменного имени и определить:

* успешно ли выполнено разрешение;
* какие адреса получены;
* какой DNS-сервер использовался, если это можно определить;
* произошло ли превышение времени ожидания;
* совпадают ли результаты повторных запросов.

Пример:

```text
DNS: example.com

Состояние: успешно
Полученные адреса:
- 93.184.216.34

Время выполнения: 48 мс
```

## Проверка веб-ресурса

С помощью `curl` необходимо определить:

* установлено ли соединение;
* получен ли HTTP-ответ;
* код ответа;
* итоговый адрес после перенаправлений;
* время выполнения;
* наличие ошибки TLS;
* наличие превышения времени ожидания.

Приложение не обязано загружать полное содержимое страницы. Достаточно выполнить запрос заголовков либо ограниченный запрос.

Пример:

```text
HTTPS: https://example.com

Состояние: доступен
Код ответа: 200
Время: 312 мс
Перенаправлений: 0
Ошибка TLS: нет
```

HTTP-коды ошибок должны отображаться как результат работы сервера, а не как внутреннее падение приложения.

## Трассировка маршрута

По результатам `tracert` или `traceroute` необходимо определить:

* количество обнаруженных переходов;
* адрес каждого ответившего узла;
* задержки до переходов;
* переходы, не давшие ответа;
* достигнута ли конечная цель;
* на каком участке появились резкие задержки или пропуски.

Пример:

```text
Маршрут до example.com:

 1   192.168.1.1       2 мс
 2   10.15.0.1         8 мс
 3   *                 нет ответа
 4   203.0.113.18      34 мс
 5   93.184.216.34     42 мс

Цель достигнута.
Переходов: 5
```

Отсутствие ответа от отдельного промежуточного узла не должно автоматически считаться обрывом маршрута, если последующие узлы или конечная цель ответили.

# 5. Анализ результатов

После полной диагностики приложение должно сформировать предполагаемое заключение.

Заключение строится на комбинации результатов, а не на одной проверке.

Необходимо различать как минимум следующие ситуации:

## Сетевой интерфейс не настроен

Признаки:

* отсутствует активный интерфейс;
* отсутствует IP-адрес;
* отсутствует маршрут по умолчанию.

Пример заключения:

```text
Предполагаемая проблема: локальная сетевая конфигурация.

На активном интерфейсе не обнаружен IP-адрес
или маршрут по умолчанию.
```

## Недоступен локальный шлюз

Признаки:

* интерфейс настроен;
* адрес шлюза известен;
* шлюз не отвечает;
* внешние узлы также недоступны.

Возможные причины:

* отключён Wi-Fi или кабель;
* проблема с маршрутизатором;
* неверная локальная конфигурация.

## Есть локальная сеть, но нет доступа в интернет

Признаки:

* шлюз доступен;
* внешние IP-адреса недоступны;
* DNS- и HTTP-проверки также не проходят.

## Возможная проблема DNS

Признаки:

* шлюз доступен;
* внешний IP-адрес доступен;
* доменное имя не разрешается;
* HTTP-запрос по доменному имени не выполняется.

## Возможная проблема конкретного сайта

Признаки:

* шлюз доступен;
* внешние IP-адреса доступны;
* DNS работает;
* другие веб-ресурсы доступны;
* выбранный ресурс недоступен.

## Нестабильное соединение

Признаки:

* превышен порог потерь пакетов;
* средняя или максимальная задержка превышает порог;
* результаты повторных проверок заметно различаются.

## Проблема не определена

Если результаты противоречивы или их недостаточно, программа не должна выдавать категоричное заключение.

Пример:

```text
Однозначно определить проблему не удалось.

Некоторые узлы не отвечают на ping,
но веб-ресурсы доступны.

Рекомендуется повторить диагностику
или передать подробный отчёт специалисту.
```

# 6. История и отчёты

Результаты полной диагностики должны сохраняться между запусками приложения.

Для каждого запуска необходимо хранить:

* уникальный идентификатор;
* дату и время;
* имя профиля;
* сведения о платформе;
* результаты всех выполненных проверок;
* итоговое заключение;
* список предупреждений.

Пользователь должен иметь возможность сравнить два результата.

Пример:

```text
Сравнение диагностик 12 и 15:

                         Диагностика 12   Диагностика 15
Потери до шлюза                 0 %              0 %
Потери до внешнего узла         2 %             18 %
Средняя задержка               34 мс            96 мс
DNS                             успешно          успешно
HTTP                            успешно          медленно
Количество переходов            8                8

Изменение:
качество внешнего соединения ухудшилось.
```

По отдельной команде программа должна формировать текстовый отчёт.

Отчёт должен содержать:

* время диагностики;
* использованный профиль;
* конфигурацию сетевых интерфейсов;
* адрес шлюза;
* результаты `ping`;
* результаты DNS-проверок;
* результаты HTTP-проверок;
* трассировку;
* итоговое заключение;
* предупреждение о неполных результатах;
* необработанный вывод утилит в отдельном разделе.

Отчёт не должен содержать сохранённые пароли Wi-Fi, данные авторизации, содержимое веб-страниц или другую конфиденциальную информацию.

# 7. Мониторинг и журналирование

Приложение должно вести журнал своей работы.

В журнал необходимо записывать:

* запуск и завершение программы;
* загрузку и проверку конфигурации;
* обнаружение операционной системы;
* проверку наличия системных утилит;
* начало и завершение диагностики;
* запуск каждой внешней команды;
* имя утилиты и цель проверки;
* код завершения внешнего процесса;
* превышение времени ожидания;
* ошибки разбора вывода;
* сформированное заключение;
* сохранение истории;
* создание отчёта;
* неизвестные команды;
* внутренние ошибки.

Пример:

```text
2026-09-14 18:20:01 INFO  Приложение запущено
2026-09-14 18:20:01 INFO  Платформа определена: windows
2026-09-14 18:20:02 INFO  Проверка утилит завершена: available=5, missing=0
2026-09-14 18:20:10 INFO  Начата диагностика: profile=home

2026-09-14 18:20:42 INFO  DNS-проверка завершена: result=success

```

В журнал не должны попадать:

* пароли;
* содержимое файлов конфигурации операционной системы;
* содержимое полученных веб-страниц;
* заголовки авторизации;
* полный пользовательский ввод, если он может содержать конфиденциальные данные.

# 8. Проверка конфигурации и обработка ошибок

Перед началом работы программа должна проверить конфигурацию.

Необходимо обнаруживать как минимум следующие ошибки:

* отсутствует профиль по умолчанию;
* профиль с указанным именем не существует;
* не задано ни одной внешней цели;
* адрес шлюза имеет неправильный формат;
* количество пакетов меньше единицы;
* время ожидания меньше единицы;
* максимальное количество переходов меньше единицы;
* порог предупреждения превышает критический порог;
* процент потерь находится вне диапазона от 0 до 100;
* HTTP-адрес имеет неправильный формат;
* путь к журналу, истории или отчётам не указан.

Приложение также должно корректно обрабатывать:

* отсутствие необходимой системной утилиты;
* отказ в запуске внешнего процесса;
* ненулевой код завершения;
* превышение времени выполнения команды;
* неожиданный или неполный формат вывода;
* различия в локализации вывода системных утилит;
* недоступность сетевого интерфейса;
* отсутствие маршрута по умолчанию;
* неизвестный узел;
* ошибку DNS;
* отказ в соединении;
* ошибку TLS;
* прерывание диагностики пользователем;
* невозможность сохранить историю или отчёт;
* повреждение файла истории;
* невозможность перезагрузить конфигурацию.

Ошибка одной проверки не должна прекращать всю диагностику, если остальные проверки всё ещё можно выполнить.

Пример:

```text
Не удалось выполнить трассировку.

Утилита: traceroute
Причина: превышено время ожидания.

Остальные проверки продолжат выполняться.
Итоговый результат будет помечен как неполный.
```

Если формат вывода утилиты не удалось распознать, программа должна сохранить его в отчёте и указать, что автоматическая обработка не выполнена.

# 9. Ограничения задания

В рамках лабораторной работы не требуется:

* самостоятельно реализовывать `ping`, DNS-клиент или трассировку;
* создавать или отправлять сетевые пакеты напрямую;
* изменять IP-адреса, DNS-серверы и маршруты;
* перезапускать сетевые интерфейсы;
* автоматически исправлять обнаруженные проблемы;
* сканировать порты;
* перехватывать сетевой трафик;
* проверять чужие локальные сети;
* обходить межсетевые экраны;
* выполнять нагрузочное тестирование;
* измерять максимальную пропускную способность;
* запускать диагностику без ведома пользователя;
* создавать графический интерфейс;
* обращаться к внешним платным API.

Проверки должны выполняться только для локального шлюза и явно заданных в конфигурации узлов.

Приложение решает задачу сбора результатов стандартных диагностических утилит, их обработки и формирования понятного заключения о предполагаемом уровне сетевой неисправности.
